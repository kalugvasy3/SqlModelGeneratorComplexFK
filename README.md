# SqlModelGenerator

[English](#english) | [Русский](#русский)

## English

Generates C# POCO classes, a DbContext, and stored procedure wrappers for an **existing SQL Server database**. Requires .NET 8; the generated code has been tested with EF Core SqlServer 8.0.27.

The generator reads system catalogs and metadata describing the first procedure result set. It **does not execute application stored procedures or create/modify database constraints**. Existing foreign keys are represented by POCO navigation properties and the DbContext Fluent API configuration.

### Running the generator

```powershell
dotnet build -c Release
# Optional: override the connection in Program.cs without editing source code.
$env:SQLMODELGENERATOR_CONNECTION_STRING = 'Server=localhost;Database=Example;Integrated Security=true;Encrypt=true;TrustServerCertificate=true'
$env:SQLMODELGENERATOR_OUTPUT = 'C:\GeneratedModels\Example'
dotnet run -c Release
```

Without these environment variables, the generator uses the existing connection string in `Program.cs` and writes to the `Generated` directory next to the executable. To read the complete schema, the account must be able to view object definitions (`VIEW DEFINITION` or equivalent permissions). Objects hidden from that account may be absent from the output.

When upgrading from the original generator, choose a **new output directory**: older files do not have the generator ownership marker. New files are marked with `// <auto-generated />`. The `.sqlmodel-files.json` manifest allows subsequent runs to remove only obsolete generated C# files. Unrelated files are not deleted; a name collision with an unmarked C# file stops publication. Keep your own additions in separate partial-class files.

All output is generated in a temporary directory first, so a generation error does not replace the previous set of files. A filesystem error during the subsequent copy can still interrupt publication.

### Generated output

- `Entities/`: tables, scalar properties, and navigation properties.
- `Views/`: keyless view classes.
- `Procedures/`: parameter/OUTPUT DTOs, first-result-set classes, and methods in a partial DbContext.
- `ProcedureSupport/`: argument-presence tracking and System.Text.Json support for parameter DTOs.
- `AppDbContext.g.cs`: table, schema, key, property, and relationship mappings.
- `Report.txt`: original-to-generated name mappings, relationships, skipped objects, and explanations.

Add the generated files to a project with the `Microsoft.EntityFrameworkCore.SqlServer` and `Microsoft.Data.SqlClient` packages. This repository uses SqlClient 5.2.2. The consuming project does not need `ImplicitUsings` enabled.

To call the generator from other code, use `ModelGenerator.Generate(model, options)`. This entry point prepares names and relationships before generating all files.

### Foreign keys

Supported relationships include single-column and composite foreign keys, cross-schema references, self-references, and multiple relationships between the same tables. Column order follows the key or constraint definition, rather than the physical order of columns in the table.

The dependent entity receives a reference to its principal. The principal receives a collection of dependent entities; when a primary key or an unfiltered unique index proves that the foreign-key columns are unique, a single inverse reference is generated instead (`WithOne`). Whether the dependent reference is required follows the nullability of its foreign-key columns. A single inverse reference can always be `null`: a principal row does not guarantee that a dependent row exists.

References to alternate unique keys use `HasPrincipalKey`. The DbContext also includes the foreign-key constraint name and DELETE actions: CASCADE, SET NULL, and NO ACTION.

Example for `Order.CustomerId -> Customer.Id`:

```csharp
// Navigation properties in the respective entity classes:
public Customer Customer { get; set; } = null!;
public ICollection<Order> OrdersViaCustomer { get; set; } = new List<Order>();

// Query with related entities loaded:
var orders = await db.Orders.Include(o => o.Customer).ToListAsync();
```

Name collisions are resolved using the schema name and/or a numeric suffix. The report lists the exact mappings. Related entities are not loaded automatically: the generator does not enable lazy-loading proxies.

Limitations:

- Bidirectional relationships involving tables without a primary key are skipped with a warning; a key is not invented.
- Disabled foreign keys are skipped. Untrusted foreign keys are mapped but flagged in the report.
- Nullable columns in a principal alternate key are incompatible with EF keys. Such relationships are skipped to preserve the columns' nullability semantics.
- Filtered unique indexes are not used to choose `WithOne`: an arbitrary filter does not prove uniqueness for all participating rows.
- ON UPDATE and DELETE SET DEFAULT have no direct equivalent in this EF model. These cases are explicitly reported; SET DEFAULT is represented as NoAction in EF, while the original behavior remains in the database.

### Generation fixes

Mappings preserve SQL types, string/binary lengths, decimal precision, nullability, identity, default/computed SQL, and rowversion. A non-identity primary key does not acquire automatic value generation merely because it is numeric.

Names from different schemas, collisions after normalization, Unicode, keywords, and conflicting property names are handled separately. SQL identifiers and C# string literals are escaped.

This is **not a complete schema export or a ready-to-use migration set**: it does not reproduce every index, CHECK constraint, trigger, permission, user-defined alias type, exact identity configuration, or other SQL Server feature. Do not use `EnsureCreated` or migrations to clone the source database without a separate review.

### Stored procedures

Result metadata is read through `sys.dm_exec_describe_first_result_set_for_object`, using metadata field names. Parameters are passed as SqlParameter objects in their original order. Fixes cover EXEC syntax, OUTPUT, Unicode/MAX lengths, keyword parameter names, and passing CancellationToken to the correct EF overload.

Methods with OUTPUT parameters have an additional optional argument after `cancellationToken`:

```csharp
var output = new Dictionary<string, object?>();
// The actual signature depends on your procedure's parameters.
await db.DoWorkAsync("text", null, null, cancellationToken: default, outputValues: output);
// Dictionary keys are original parameter names including @; SQL NULL becomes null.
```

If the result cannot be described (for example, because of dynamic SQL or temporary tables), or its columns lack distinct SQL aliases, the reason is included in the report. Instead of generating an incorrect ExecuteNonQuery call, the generator emits a method that throws `NotSupportedException` before accessing the database.

Wrappers support only the **first result set**. `Task<List<T>>` loads that result entirely into memory; large results and multiple result sets need a separate streaming/DataSet interface. A procedure's SQL RETURN code is not exposed. For procedures without a result set, `Task<int>` returns the affected-row count according to ExecuteNonQuery semantics (which can be -1 with NOCOUNT). Scalar overloads always supply all their arguments. Object overloads can request SQL DEFAULT as described below.

Unsupported types (for example, CLR spatial types or table-valued parameters without a dedicated adapter) are not silently mapped to string: table metadata reading stops with an error identifying the column, while an unsupported procedure receives a diagnostic stub.

#### Parameter and OUTPUT classes

For each procedure whose parameter metadata is complete, the generator also creates:

- `<Procedure>Parameters`: all input parameters, including initial values for INPUT/OUTPUT parameters. Parameterless procedures receive an empty class.
- `<Procedure>Output`: typed OUTPUT values, only when the procedure has OUTPUT parameters.
- `<Procedure>Result`: the existing first-result-row class, when its schema is known.

These classes are generated in C# and, when TypeScript generation is enabled, in TypeScript. Names use the established collision handling; `Report.txt` lists their actual names. A missing/unsupported result schema does not prevent generation of a known parameter contract, but the procedure method remains a diagnostic stub. Incomplete parameter metadata does not produce a misleading partial DTO.

Existing methods with separate arguments and an optional output dictionary remain available. An additional overload accepts the parameter object and an optional typed output object. The result is still the existing `Task<List<T>>` or `Task<int>`; the output object is filled after successful execution.

```csharp
// Illustrative procedure with CustomerId and StartDate input parameters:
var parameters = new GetOrdersParameters
{
    CustomerId = 42,
    StartDate = startDate
};
var rows = await db.GetOrdersAsync(parameters, cancellationToken);
```

For the sample `DoWork` signature shown earlier:

```csharp
var parameters = new DoWorkParameters
{
    Class = "text",
    CancellationToken = null, // Initial value of the SQL INPUT/OUTPUT parameter.
    P0 = null                 // Initial value of the other SQL INPUT/OUTPUT parameter.
};
var output = new DoWorkOutput();
var affectedRows = await db.DoWorkAsync(parameters, cancellationToken: default, outputValues: output);
// output.CancellationToken and output.P0 are typed properties, not dictionary entries.
```

The DTO overload uses an inferred generic parameter so legacy calls such as `MethodAsync(null)` and `MethodAsync(default)` do not become ambiguous. No explicit generic type argument is needed.

C# input properties use the generated `ProcedureSupport.ProcedureArgument<T>` value wrapper with implicit conversion from `T`. Object initializers therefore still use ordinary assignments. It records presence separately from the value:

| Input assignment | SQL meaning |
| --- | --- |
| Not assigned, or reset to `default` | Request `DEFAULT` for that argument |
| Explicit `null` on a nullable property | Send SQL `NULL` |
| Any value, including `0` or `false` | Send that value |

To inspect an input in C#, use `parameters.CustomerId.IsSpecified` and then `parameters.CustomerId.GetValue()`. `GetValue()` throws for an unspecified input. SQL Server checks whether a requested default actually exists; the generator does not guess defaults or application-level requiredness from `sys.parameters`, which does not maintain T-SQL defaults. [SQL Server metadata documentation](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-parameters-transact-sql?view=sql-server-ver17)

An INPUT/OUTPUT parameter must be explicitly initialized, including with `null` if only its returned value is needed. An omitted OUTPUT argument is rejected before execution: it cannot safely request the procedure's default and simultaneously bind an output variable without knowing that default. Returned OUTPUT properties allow `null` to represent SQL NULL. The SQL RETURN status code is still separate and is not captured by these wrappers.

The supplied System.Text.Json converter keeps the JSON contract flat:

```json
{ "customerId": 42, "startDate": null }
```

Missing fields remain unspecified; explicitly supplied nulls remain supplied, including after a JSON round trip. No `isSpecified` or wrapper object is sent. TypeScript input fields are optional to express a request for SQL DEFAULT, **not a guarantee that SQL accepts omission**. INPUT/OUTPUT fields must be present and may be null. The converter is for System.Text.Json JSON bodies; query-string binding, Newtonsoft.Json, custom OpenAPI schema descriptions, and Native AOT/source-generated serializer integration need their own adapters or configuration. API business validation remains the application's responsibility.

### Optional TypeScript classes for Angular

Two optional settings control TypeScript generation. Both are available near the top of `Program.cs`:

```csharp
private const bool BuildTypeScriptClasses = false;
private const string? TypeScriptOutputFolder = null;
```

To enable it, set both values, for example:

```csharp
private const bool BuildTypeScriptClasses = true;
private const string? TypeScriptOutputFolder = @"C:\MyAngularApp\src\app\models\generated";
```

Alternatively, override the settings without editing or rebuilding the generator:

```powershell
$env:SQLMODELGENERATOR_BUILD_TYPESCRIPT_CLASSES = 'True'
$env:SQLMODELGENERATOR_TYPESCRIPT_OUTPUT = 'C:\MyAngularApp\src\app\models\generated'
dotnet run -c Release
```

Environment variables override the corresponding `Program.cs` defaults. The flag accepts `True`/`False`, ignoring case; other nonempty values are rejected before reading the database. TypeScript generation runs **only when the flag is true and the folder is nonempty**. If the settings are absent, false, or incomplete, only C# is generated. Existing TypeScript files are left untouched when disabled. The C# and TypeScript output folders must be different.

For use from C# code, the same two optional parameters follow the original three `CodeGeneratorOptions` parameters:

```csharp
var options = new CodeGeneratorOptions(
    RootNamespace: "GeneratedModel",
    OutputRoot: @"C:\GeneratedModels\CSharp",
    DbContextName: "AppDbContext",
    BuildTypeScriptClasses: true,
    TypeScriptOutputFolder: @"C:\GeneratedModels\TypeScript");
```

The separate TypeScript folder contains:

- `entities/*.ts`: table classes with navigation properties.
- `views/*.ts`: view classes.
- `procedures/*.ts`: parameter/OUTPUT DTOs and supported first-result-set classes; no database execution code is generated for the browser.
- `index.ts`: exports for importing models from one place.
- `.sqlmodel-typescript-files.json`: ownership manifest for removing obsolete generated TypeScript files on subsequent enabled runs.

Classes have no Angular or third-party runtime dependency. Names match the generated C# classes; properties follow ASP.NET Core's standard camelCase JSON naming policy (`CustomerId` becomes `customerId`, `URLValue` becomes `urlValue`). Type-only imports support relationships, including cycles, without constructing related objects.

| SQL value | TypeScript JSON type |
| --- | --- |
| bit | `boolean` |
| Integer, floating-point, decimal and money types | `number` |
| Text, XML, GUID | `string` |
| Date/time and TimeSpan | `string` |
| Binary and rowversion | Base64 `string` |
| sql_variant | `unknown` |
| Nullable scalar column | The mapped type with `\| null` |

Navigation properties are optional and allow `null`, because an API can omit unloaded or ignored relationships. These are descriptions of the generated POCOs' default JSON representation, not automatic discovery of your endpoint DTOs. Custom serialization or DTO projections may require a different contract.

JavaScript `number` cannot preserve all SQL bigint integers or decimal/money values exactly. The generator follows default JSON numeric serialization and adds notes to the generated fields and report. If exact large IDs or decimal precision is required, use string-valued API DTOs and corresponding frontend types; merely changing a TypeScript annotation cannot recover precision lost while parsing JSON.

```typescript
import type { Customer } from './models/generated';

// Example inside an Angular service with an injected HttpClient:
getCustomer(id: number) {
  return this.http.get<Customer>(`/api/customers/${id}`);
}
```

The classes contain declarations, without default values or conversion logic. An HTTP JSON response is still a plain object; a generic type argument does not construct a class or convert date strings to `Date`. If an actual instance is needed, explicitly assign the response to `new Customer()`; nested objects still require separate conversion.

Both C# and TypeScript outputs are generated and checked for ownership collisions before either is published. Files without the generated marker are protected. An I/O failure during copying can still interrupt publication; there is no cross-directory transaction. The disabled mode never reads, cleans, or creates the TypeScript output folder.

### Local checks

The generator itself does not need Node.js. The TypeScript regression checks require Node.js and a TypeScript compiler (tested with 5.9.3).

```powershell
# Install the test-only TypeScript dependency once:
npm --prefix .\Tests\TypeScriptSmoke install
.\Tests\Run-Tests.ps1
# If dependencies have already been restored:
.\Tests\Run-Tests.ps1 -NoRestore
```

A compiler already installed elsewhere can be supplied with `-TypeScriptCompiler "C:\path\to\typescript\lib\typescript.js"`. Generated TypeScript is checked with strict nullability, `exactOptionalPropertyTypes`, `isolatedModules`, and type-only imports, followed by runtime JSON checks. The on/off/missing-folder cases and file ownership are also covered. Procedure DTO checks include old-call compatibility, typed outputs, SQL DEFAULT/NULL/zero, flat JSON round trips, and ASP.NET Core model validation.

The checks construct synthetic schemas, generate actual C# files, compile them with warnings treated as errors, and validate the EF model. Procedure commands are intercepted locally to check SQL, OUTPUT/DBNull, SqlParameter sizes, CancellationToken, and row materialization. SQL connection opening is suppressed in these tests.

Coverage includes composite/alternate keys, required/optional and cyclic relationships, naming collisions, columns containing quotes/brackets, an empty schema, views-only and procedures-only schemas, and repeated generation. These checks do not replace verification of permissions and the specific production schema on SQL Server.

## Русский

Генератор C# POCO, DbContext и обёрток хранимых процедур для **существующей базы SQL Server**. Требуется .NET 8; сгенерированный код проверен с EF Core SqlServer 8.0.27.

Генератор читает системные каталоги и описание первого результата процедур. Он **не выполняет пользовательские процедуры и не создаёт/изменяет ограничения в базе**. Внешние ключи существующей базы описываются в POCO и Fluent API DbContext.

### Запуск

```powershell
dotnet build -c Release
# Необязательно: переопределить подключение из Program.cs без правки исходников.
$env:SQLMODELGENERATOR_CONNECTION_STRING = 'Server=localhost;Database=Example;Integrated Security=true;Encrypt=true;TrustServerCertificate=true'
$env:SQLMODELGENERATOR_OUTPUT = 'C:\GeneratedModels\Example'
dotnet run -c Release
```

Без этих переменных используются прежнее подключение из Program.cs и каталог `Generated` рядом с исполняемым файлом. Для полноценного чтения схемы учётная запись должна видеть определения объектов (`VIEW DEFINITION` или эквивалентные права). Скрытые для неё объекты могут отсутствовать в результате.

После первого обновления генератора выбирайте **новую папку вывода**: старые файлы не имели отметки принадлежности генератору. Новые файлы помечаются `// <auto-generated />`. Манифест `.sqlmodel-files.json` позволяет при повторном запуске удалять только устаревшие сгенерированные C#-файлы. Посторонние файлы не удаляются; совпадение имени с непомеченным C#-файлом останавливает запись. Собственные дополнения храните в отдельных partial-классах.

Весь результат сначала генерируется во временном каталоге; ошибка генерации не заменяет предыдущий набор. Ошибка файловой системы во время последующего копирования всё же может прервать публикацию.

### Результат

- `Entities/`: таблицы, скалярные свойства и навигационные свойства.
- `Views/`: представления без ключей.
- `Procedures/`: DTO параметров/OUTPUT, классы первого результата и методы в partial DbContext.
- `ProcedureSupport/`: отслеживание присутствия аргументов и поддержка System.Text.Json для DTO.
- `AppDbContext.g.cs`: таблицы, схемы, ключи, свойства и связи.
- `Report.txt`: соответствие исходных/сгенерированных имён, связи, пропущенные объекты и причины.

Добавьте сгенерированные файлы в проект с пакетами `Microsoft.EntityFrameworkCore.SqlServer` и `Microsoft.Data.SqlClient`. В этом репозитории используется SqlClient 5.2.2. `ImplicitUsings` в принимающем проекте не требуется.

Для использования генератора из другого кода вызывайте `ModelGenerator.Generate(model, options)`: этот вход подготавливает имена и связи перед генерацией всех файлов.

### Внешние ключи

Поддерживаются простые и составные FK, ссылки между схемами, ссылки таблицы на себя и несколько разных связей между одними таблицами. Порядок столбцов сохраняется по порядку ключа/ограничения, а не по расположению колонок в таблице.

На стороне дочерней таблицы появляется ссылка на родителя. На стороне родителя — коллекция дочерних объектов; если уникальность FK доказана первичным ключом или нефильтрованным уникальным индексом, генерируется одиночная обратная ссылка (`WithOne`). Обязательность ссылки соответствует nullable-колонкам FK. Обратная одиночная ссылка всегда может быть `null`: наличие родителя не гарантирует наличие дочерней записи.

Ссылки на альтернативные уникальные ключи описываются через `HasPrincipalKey`. В DbContext также записываются имя FK и действия DELETE: CASCADE, SET NULL, NO ACTION.

Пример для `Order.CustomerId -> Customer.Id`:

```csharp
// Навигационные свойства:
public Customer Customer { get; set; } = null!;
public ICollection<Order> OrdersViaCustomer { get; set; } = new List<Order>();

// Запрос с загрузкой связанных объектов:
var orders = await db.Orders.Include(o => o.Customer).ToListAsync();
```

При совпадениях имён добавляются схема и/или числовой суффикс. Точное соответствие доступно в отчёте. Ссылки не загружаются автоматически: генератор не включает lazy-loading proxies.

Ограничения:

- Для таблиц без PK двусторонняя связь пропускается с предупреждением; ключ не выдумывается.
- Отключённые FK пропускаются. Недоверенные FK отображаются, но отмечаются в отчёте.
- Nullable-колонки альтернативного ключа родителя несовместимы с ключами EF: такая связь пропускается, чтобы не менять nullable-семантику столбцов.
- Фильтрованные уникальные индексы не используются для определения `WithOne`: произвольный фильтр не доказывает уникальность всех участвующих строк.
- ON UPDATE и DELETE SET DEFAULT не имеют прямого эквивалента в этой модели EF. Эти случаи явно отмечаются в отчёте; SET DEFAULT представлен как NoAction на стороне EF, исходное поведение остаётся в базе.

### Исправления генерации

Сохраняются SQL-типы, длина строк/двоичных колонок, точность decimal, nullable, identity, default/computed SQL и rowversion. Неidentity PK не получает автоматическую генерацию значения только потому, что он числовой.

Имена из разных схем, совпадения после нормализации, Unicode, ключевые слова и конфликтующие имена свойств обрабатываются отдельно. SQL-идентификаторы и C#-строки экранируются.

Это **не полный перенос схемы и не готовый набор миграций**: не воспроизводятся все индексы, CHECK, триггеры, права, пользовательские alias-типы, точные параметры identity и другие особенности SQL Server. Не используйте `EnsureCreated`/миграции как способ клонировать исходную базу без отдельной проверки.

### Процедуры

Описание результата читается через `sys.dm_exec_describe_first_result_set_for_object`, по именам полей метаданных. Параметры передаются как SqlParameter в исходном порядке. Исправлены EXEC, OUTPUT, длины Unicode/MAX, параметры с именами-ключевыми словами и передача CancellationToken в нужную перегрузку EF.

Методы с OUTPUT имеют дополнительный необязательный аргумент после `cancellationToken`:

```csharp
var output = new Dictionary<string, object?>();
// Конкретная сигнатура зависит от параметров вашей процедуры.
await db.DoWorkAsync("text", null, null, cancellationToken: default, outputValues: output);
// Ключи словаря — исходные имена параметров с @; SQL NULL представлен как null.
```

Если результат нельзя описать (например, dynamic SQL или временные таблицы) либо у колонок нет уникальных SQL-псевдонимов, причина попадает в отчёт. Вместо ошибочного ExecuteNonQuery генерируется метод, явно выбрасывающий `NotSupportedException` до обращения к базе.

Обёртки поддерживают только **первый результат**. `Task<List<T>>` загружает его целиком в память; для больших результатов и нескольких таблиц нужен отдельный потоковый/DataSet-интерфейс. SQL RETURN-код процедуры не возвращается; `Task<int>` без результата — количество затронутых строк по правилам ExecuteNonQuery (оно может быть -1 при NOCOUNT). Скалярные перегрузки передают все аргументы. Перегрузки с объектом могут запрашивать SQL DEFAULT, как описано ниже.

Неподдержанные типы (например, CLR spatial-типы или табличные параметры без специального адаптера) не маскируются под string: для таблицы чтение завершается с указанием столбца, для процедуры создаётся диагностическая заглушка.

#### Классы параметров и OUTPUT

Для каждой процедуры с полностью прочитанными параметрами дополнительно создаются:

- `<Procedure>Parameters` — входные параметры, включая начальные значения INPUT/OUTPUT. Для процедуры без параметров создаётся пустой класс.
- `<Procedure>Output` — типизированные значения OUTPUT, если такие параметры есть.
- `<Procedure>Result` — уже существующий класс строки первого результата, когда его схема известна.

Классы создаются в C# и, при включённой генерации TypeScript, в TypeScript. Совпадения имён разрешаются по общим правилам; точные имена записываются в `Report.txt`. Если схема результата неизвестна, но параметры прочитаны полностью, класс параметров всё равно создаётся, а метод процедуры остаётся диагностической заглушкой. Неполный список параметров не превращается в вводящий в заблуждение DTO.

Существующие методы с отдельными аргументами и необязательным словарём OUTPUT сохраняются. Добавляется перегрузка с объектом параметров и необязательным типизированным объектом OUTPUT. Возвращаемое значение остаётся прежним `Task<List<T>>` или `Task<int>`; объект OUTPUT заполняется после успешного выполнения.

```csharp
// Пример процедуры с входными CustomerId и StartDate:
var parameters = new GetOrdersParameters
{
    CustomerId = 42,
    StartDate = startDate
};
var rows = await db.GetOrdersAsync(parameters, cancellationToken);
```

Для приведённого выше примера `DoWork`:

```csharp
var parameters = new DoWorkParameters
{
    Class = "text",
    CancellationToken = null, // Начальное значение SQL-параметра INPUT/OUTPUT.
    P0 = null                 // Начальное значение второго INPUT/OUTPUT.
};
var output = new DoWorkOutput();
var affectedRows = await db.DoWorkAsync(parameters, cancellationToken: default, outputValues: output);
// output.CancellationToken и output.P0 — типизированные свойства, а не элементы словаря.
```

Перегрузка использует выводимый компилятором generic-параметр: это сохраняет однозначность старых вызовов `MethodAsync(null)` и `MethodAsync(default)`. Указывать generic-тип вручную не требуется.

Входные C#-свойства используют сгенерированную обёртку `ProcedureSupport.ProcedureArgument<T>` с неявным преобразованием из `T`. Поэтому в инициализаторе остаётся обычное присваивание. Обёртка различает наличие значения и само значение:

| Присваивание входному параметру | Значение для SQL |
| --- | --- |
| Не присвоено или сброшено через `default` | Запросить `DEFAULT` |
| Явно присвоен `null` nullable-свойству | Передать SQL `NULL` |
| Любое значение, включая `0` и `false` | Передать это значение |

Для чтения в C# используются `parameters.CustomerId.IsSpecified` и затем `parameters.CustomerId.GetValue()`. Для незаданного аргумента `GetValue()` выбрасывает исключение. Наличие DEFAULT проверяет SQL Server: генератор не угадывает значения по умолчанию или бизнес-обязательность по `sys.parameters`, где DEFAULT для T-SQL не поддерживается. [Документация SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-parameters-transact-sql?view=sql-server-ver17)

INPUT/OUTPUT нужно явно инициализировать — можно `null`, если интересует только выходное значение. Пропущенный OUTPUT отклоняется до выполнения: нельзя безопасно одновременно запросить неизвестный DEFAULT процедуры и привязать выходную переменную. Выходные свойства допускают `null` для SQL NULL. Код SQL RETURN остаётся отдельным механизмом и этими обёртками не возвращается.

Конвертер System.Text.Json сохраняет обычный JSON:

```json
{ "customerId": 42, "startDate": null }
```

Отсутствующие поля остаются незаданными, явно переданные null — заданными, в том числе после сериализации обратно в JSON. Служебные флаги и объекты-обёртки не передаются. Необязательные входные поля TypeScript означают возможность запросить SQL DEFAULT, **а не гарантию, что SQL допускает пропуск**. Поля INPUT/OUTPUT обязательны в объекте и допускают null. Конвертер рассчитан на JSON-тело System.Text.Json; привязка query string, Newtonsoft.Json, описание схем OpenAPI и Native AOT/source-generated сериализация требуют отдельных адаптеров или настройки. Бизнес-валидация API остаётся ответственностью приложения.

### Необязательные TypeScript-классы для Angular

Два необязательных параметра находятся в начале `Program.cs`:

```csharp
private const bool BuildTypeScriptClasses = false;
private const string? TypeScriptOutputFolder = null;
```

Для включения задай оба значения:

```csharp
private const bool BuildTypeScriptClasses = true;
private const string? TypeScriptOutputFolder = @"C:\MyAngularApp\src\app\models\generated";
```

Можно переопределить их без правки и пересборки генератора:

```powershell
$env:SQLMODELGENERATOR_BUILD_TYPESCRIPT_CLASSES = 'True'
$env:SQLMODELGENERATOR_TYPESCRIPT_OUTPUT = 'C:\MyAngularApp\src\app\models\generated'
dotnet run -c Release
```

Переменные окружения имеют приоритет над значениями в `Program.cs`. Флаг принимает `True`/`False` без учёта регистра; иные непустые значения отклоняются до чтения базы. TypeScript создаётся **только при true и непустой папке**. Если параметры отсутствуют, выключены или заданы не полностью, генерируется только C#. Уже существующие TypeScript-файлы при выключенном режиме не меняются. Папки C# и TypeScript должны различаться.

При вызове из C# эти же два необязательных параметра идут после исходных трёх параметров `CodeGeneratorOptions`:

```csharp
var options = new CodeGeneratorOptions(
    RootNamespace: "GeneratedModel",
    OutputRoot: @"C:\GeneratedModels\CSharp",
    DbContextName: "AppDbContext",
    BuildTypeScriptClasses: true,
    TypeScriptOutputFolder: @"C:\GeneratedModels\TypeScript");
```

В отдельной TypeScript-папке создаются:

- `entities/*.ts` — классы таблиц с навигационными свойствами.
- `views/*.ts` — классы представлений.
- `procedures/*.ts` — DTO параметров/OUTPUT и классы поддержанных первых результатов; код выполнения запросов в браузере не генерируется.
- `index.ts` — общий экспорт моделей.
- `.sqlmodel-typescript-files.json` — манифест для удаления устаревших сгенерированных TypeScript-файлов при повторном включённом запуске.

Классы не зависят от Angular или сторонних библиотек. Имена классов совпадают с C#, свойства соответствуют стандартному camelCase JSON ASP.NET Core: `CustomerId` → `customerId`, `URLValue` → `urlValue`. Связи используют `import type`, включая циклические ссылки, без автоматического создания связанных объектов.

| Значение SQL | Тип TypeScript в JSON |
| --- | --- |
| bit | `boolean` |
| Целые, вещественные, decimal и money | `number` |
| Текст, XML, GUID | `string` |
| Дата/время и TimeSpan | `string` |
| Двоичные значения и rowversion | Base64 `string` |
| sql_variant | `unknown` |
| Nullable-колонка | Тип с добавлением `\| null` |

Навигационные свойства необязательны и допускают `null`: API может не отдавать незагруженные или исключённые связи. Модели описывают стандартное JSON-представление сгенерированных POCO, а не автоматически обнаруженные DTO твоих endpoint-ов. Собственная сериализация или DTO могут требовать другого контракта.

JavaScript `number` не сохраняет точно все значения SQL bigint и decimal/money. Генератор следует стандартному числовому JSON-представлению и добавляет пояснения в поля и отчёт. Для точных больших идентификаторов и десятичных значений нужны строковые DTO на backend и соответствующие frontend-типы; одна TypeScript-аннотация не восстановит точность, потерянную при разборе JSON.

```typescript
import type { Customer } from './models/generated';

// Пример внутри Angular-сервиса с внедрённым HttpClient:
getCustomer(id: number) {
  return this.http.get<Customer>(`/api/customers/${id}`);
}
```

Классы содержат объявления без начальных значений и преобразований. JSON-ответ остаётся обычным объектом: указание типа не создаёт экземпляр класса и не превращает строку даты в `Date`. При необходимости данные можно явно присвоить `new Customer()`; вложенные объекты при этом требуют отдельного преобразования.

Оба набора файлов сначала генерируются и проверяются на конфликты принадлежности, затем публикуются. Непомеченные пользовательские файлы защищены. Ошибка ввода-вывода во время копирования всё же может прервать публикацию: общей транзакции для двух папок нет. Выключенный режим вообще не читает, не очищает и не создаёт TypeScript-папку.

### Локальные проверки

Самому генератору Node.js не нужен. Для TypeScript-проверок нужны Node.js и компилятор TypeScript (проверено с 5.9.3).

```powershell
# Один раз установить TypeScript только для тестов:
npm --prefix .\Tests\TypeScriptSmoke install
.\Tests\Run-Tests.ps1
# Если зависимости уже восстановлены:
.\Tests\Run-Tests.ps1 -NoRestore
```

Уже установленный компилятор можно указать через `-TypeScriptCompiler "C:\path\to\typescript\lib\typescript.js"`. TypeScript проверяется в строгом режиме с `exactOptionalPropertyTypes`, `isolatedModules` и импортами типов, затем проверяется работа классов с JSON. Дополнительно проверены включение/выключение, отсутствие папки и защита пользовательских файлов. Для DTO проверены старые вызовы, типизированный OUTPUT, SQL DEFAULT/NULL/ноль, JSON и валидация ASP.NET Core.

Проверки строят синтетические схемы, генерируют настоящие C#-файлы, компилируют их с предупреждениями как ошибками и проверяют модель EF. Команды процедур перехватываются локально: проверяются SQL, OUTPUT/DBNull, размеры SqlParameter, CancellationToken и материализация строк. Открытие SQL-соединений в этих тестах подавлено.

Проверяются составные/альтернативные ключи, обязательные/необязательные и циклические связи, совпадения имён, столбцы с кавычками/скобками, пустая схема, только views, только procedures и повторная генерация. Это не заменяет проверку прав и особенностей конкретной рабочей схемы на SQL Server.
